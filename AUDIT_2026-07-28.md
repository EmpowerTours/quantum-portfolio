# Security Audit — quantum-portfolio

**Date**: 2026-07-28
**Scope**: `contracts/src/**` (incl. live Monad mainnet deployments), `src/**` (Python pipeline),
`zk-mldsa/{program,lib}` (SP1 guest), dependency trees, secret hygiene.
**Method**: static review + on-chain state checks (`cast` against `https://rpc.monad.xyz`) +
executable proof-of-concept (`contracts/test/AuditPoC_DustDoS.t.sol`) + `pip-audit`.

---

## Executive Summary

Three issues warrant action before this is presented as production-grade. Two are **live on Monad
mainnet right now**: `UniswapRoutingVault` and `MorphoSupplyAdapter` can each be **permanently
bricked by an unsolicited 1-wei token transfer**, with no rescue path and no owner. I verified both
contracts currently hold zero balance, so neither has been griefed yet — but the window is open.

The third is a **soundness gap in the ZK attestation**: the SP1 guest treats the ML-DSA public key
as a private input and commits only `orderHash`, so a valid Groth16 proof attests "*somebody's*
key signed something hashing to X", not "*the agent's* key did". Anyone can mint a valid
attestation for an arbitrary order hash. Nothing gates on `pqAttested` today, so no funds are at
risk — but `MLDSAAttestation`'s own NatSpec invites the vault/adapter to gate on it, which would
turn this into an authorization bypass. It also undercuts the submission's headline claim.

The same key-pinning omission exists in the Python verifier. Everything else is in good shape:
no secrets in tracked files, no private-key handling in the tx builder, 45/45 tests passing.

## HIGH

### H-1 — Permanent DoS: 1-wei WMON donation bricks `UniswapRoutingVault` forever
**File**: `contracts/src/UniswapRoutingVault.sol:160-161`
**Live at**: `0xe2fcada067227c817b8a47b850d727ba065e16dd` (Monad mainnet, chainId 143)
**Status**: exploitable now; current WMON balance verified `0` (not yet griefed)

```solidity
uint256 residual = IERC20(address(WRAPPED_MON)).balanceOf(address(this));
if (residual != 0) revert WMonDustResidual(residual);
```

The invariant is written against the **absolute** balance. The vault is stateless — it holds no
WMON between calls — so the check is intended to read "we consumed everything we wrapped". But
ERC-20 transfers are push-based and unsolicited: anyone can `transfer(vault, 1)` WMON. From that
moment the residual is permanently ≥ 1 and **every** `executeAndRoute` call reverts, for every
user, forever. There is no owner, no `rescue`, no sweep, and the allowlist is immutable — the only
recovery is redeploying the vault and migrating.

Attack cost: 1 wei of WMON (~$2.3e-20 at MON ≈ $0.023) plus gas.

**PoC** (passing): `test_PoC_OneWeiWMonDonationBricksVaultForever` in
`contracts/test/AuditPoC_DustDoS.t.sol` — donates 1 wei, then shows two independent, otherwise
valid orders both revert with `WMonDustResidual(1)`.

**Fix** — make the invariant relative to the balance at entry:

```solidity
function executeAndRoute(...) external payable nonReentrant {
    ...
    uint256 balBefore = IERC20(address(WRAPPED_MON)).balanceOf(address(this));
    WRAPPED_MON.deposit{value: msg.value}();
    IERC20(address(WRAPPED_MON)).forceApprove(address(ROUTER), msg.value);

    ... // swap loop unchanged

    IERC20(address(WRAPPED_MON)).forceApprove(address(ROUTER), 0);
    uint256 balAfter = IERC20(address(WRAPPED_MON)).balanceOf(address(this));
    // We must end holding exactly what we started with: the whole deposit was deployed.
    if (balAfter != balBefore) revert WMonDustResidual(balAfter - balBefore);
    ...
}
```

This preserves the real safety property (the full `msg.value` was routed, nothing stranded) while
making donated dust inert. Consider also adding a permissionless `sweepDust()` that pushes any
excess to a burn/treasury address, so donations cannot accumulate.

### H-3 — ZK attestation does not bind the signing key: any order hash can be attested
**Files**: `zk-mldsa/lib/src/lib.rs:12-14`, `zk-mldsa/program/src/main.rs:20-33`,
`zk-mldsa/contracts/src/MLDSAAttestation.sol`
**Live at**: `0xc1a82D8C4D28Eca8B318D1bac8DCc2Ab963b3839` (Monad mainnet)

The guest reads `pk`, `msg`, `sig` all as untrusted inputs and commits **only** the order hash:

```rust
struct PublicValuesStruct { bytes32 orderHash; }   // pk is NOT committed
```

So the statement proven is:

> ∃ (pk, sig) such that `pk` verifies `sig` over some message `m`, and `SHA-256(m) == orderHash`.

The existential quantifier over `pk` is the problem. An attacker generates their own ML-DSA-65
keypair, signs any order they invent, runs the guest, produces a valid Groth16 proof, and calls
`attest()`. The proof verifies, and `pqAttested[theirHash]` becomes `true`. The attestation
therefore proves *that a signature exists*, not *that the agent authorized the order* — which is
the property the contract's NatSpec claims ("the agent's PQ-signed order `orderHash` is
authentic").

**Impact today**: no funds at risk — neither the vault nor the adapter reads `pqAttested`. The
damage is to the integrity of the claim. **Impact if acted on**: `MLDSAAttestation`'s own docs say
"which the AuditAnchor / vault / adapter can gate on for quantum-safe settlement". Wiring that gate
without fixing this would be a complete authorization bypass.

**Fix** — commit the key and pin it on-chain:

```rust
// zk-mldsa/lib/src/lib.rs
sol! {
    struct PublicValuesStruct {
        bytes32 orderHash;
        bytes32 pkHash;      // SHA-256 (or keccak) of the ML-DSA-65 public key
    }
}
```

```rust
// zk-mldsa/program/src/main.rs
let order_hash = verify_and_digest(&pk, &msg, &sig).expect("ML-DSA-65 verification failed");
let pk_hash: [u8; 32] = Sha256::digest(&pk).into();
let bytes = PublicValuesStruct::abi_encode(&PublicValuesStruct {
    orderHash: order_hash.into(),
    pkHash: pk_hash.into(),
});
```

```solidity
// MLDSAAttestation.sol
bytes32 public immutable agentPkHash;   // set at construction

error UnknownSigner(bytes32 got);

function attest(bytes calldata _publicValues, bytes calldata _proofBytes)
    external returns (bytes32 orderHash)
{
    ISP1Verifier(verifier).verifyProof(mldsaProgramVKey, _publicValues, _proofBytes);
    PublicValuesStruct memory pv = abi.decode(_publicValues, (PublicValuesStruct));
    if (pv.pkHash != agentPkHash) revert UnknownSigner(pv.pkHash);
    orderHash = pv.orderHash;
    pqAttested[orderHash] = true;
    emit PQOrderAttested(orderHash);
}
```

This changes the program vkey, so the guest must be rebuilt, a new Groth16 fixture generated, and
`MLDSAAttestation` redeployed. Until then, describe the attestation honestly as *"proves a valid
ML-DSA-65 signature exists over this order hash"* — not *"proves the agent signed it"*.

## MEDIUM

### M-1 — Python `verify_signed_order` trusts the public key embedded in the artifact
**File**: `src/orders.py:251-266`

```python
pk  = base64.b64decode(signed.public_key_b64)   # from the same file as the signature
sig = base64.b64decode(signed.signature_b64)
if not pq.verify(payload, sig, pk): return False
```

All three legs (ML-DSA, SLH-DSA, Ed25519) verify against keys carried *inside the signed-order
JSON*. An attacker who can modify `outputs/signed_orders.json` generates three fresh keypairs,
re-signs the tampered order, and replaces both the key and signature fields — verification passes.
The hash chain does not help: the same attacker recomputes every `prev_hash`.

This directly contradicts the docstrings in `pq_signing.py:5` and `orders.py:98-99`
("An attacker must break ALL THREE to forge an order"). Forgery requires breaking **zero** schemes
— only file-write access. The genuine trust anchor is the on-chain `AuditAnchor`, not the
signature check.

**Fix** — pin the expected keys and compare before verifying:

```python
# src/orders.py
TRUSTED_KEYS_PATH = Path("keys")

def verify_signed_order(signed, seen_nonces=None, keys_path=TRUSTED_KEYS_PATH, require_pinned=True):
    ...
    pk = base64.b64decode(signed.public_key_b64)
    if require_pinned:
        expected = (Path(keys_path) / "pq.pub").read_bytes()
        if not hmac.compare_digest(pk, expected):
            return False          # unknown signer — reject before any crypto
    ...
```

Apply the same pinning to `slh.pub` and `ed25519.pub`. Keep an explicit
`require_pinned=False` escape hatch for third parties verifying a shipped artifact against a
published key, and document that path.

### M-2 — The anchor "provenance gate" is not authorization
**Files**: `UniswapRoutingVault.sol:120`, `MorphoSupplyAdapter.sol:78`, `AuditAnchor.sol:56-86`

`AuditAnchor.anchor()` is permissionless and unauthenticated — any address can anchor any 32 bytes
for ~30k gas. So `ANCHOR.lastHash(msg.sender) != orderHash` is satisfiable by anyone in a single
preceding transaction with an arbitrary hash. It is a *bookkeeping link*, not a gate.

Not exploitable for fund loss — both contracts are non-custodial (`recipient: msg.sender`,
`onBehalf = msg.sender`), so a caller can only move their own money. The issue is that the code
comments ("provenance gate — links this trade to the off-chain QPU result + PQ signature") and the
submission narrative imply a security property the contract does not enforce. No signature is ever
checked on-chain.

**Fix**: either soften the wording to "provenance *label*", or, once H-3 is fixed, make it real by
gating on `MLDSAAttestation.pqAttested[orderHash]` in addition to the anchor.

### M-3 — Vulnerable dependencies in the Python environment
`pip-audit` reports (distinct advisories): `pillow` 12.2.0 ×14, `starlette` 1.0.1 ×5,
`gitpython` 3.1.50 ×5, `python-multipart` 0.0.29 ×3, `msgpack` 1.1.2, `setuptools` 82.0.1,
`pip` 26.1.1.

All are Streamlit transitive dependencies, not core pipeline deps. Exposure is limited because the
server binds `127.0.0.1:8501` with XSRF protection on — but `pillow` parses untrusted images and
`starlette`/`python-multipart` parse untrusted request bodies, so a demo exposed over a tunnel
would be reachable.

**Fix**: `pip install -U pillow starlette python-multipart gitpython msgpack setuptools pip`,
then pin in `requirements.txt` and re-run `pip-audit`.

### M-4 — `MorphoSupplyAdapter` does not validate the target market
**File**: `contracts/src/MorphoSupplyAdapter.sol:71-86`

Only `params.loanToken` is allowlisted. `collateralToken`, `oracle`, `irm`, and `lltv` are
entirely caller-supplied, and the resulting `marketId` is never checked against a set of known-good
markets. A malicious frontend could route a user's approved USDC into an attacker-created market
with a worthless oracle/IRM. The user's funds move to a market they did not intend, and the
`Supplied` event still looks legitimate.

**Fix**: add an immutable allowlist of `marketId`s (or of `(oracle, irm, lltv)` triples) alongside
the loan-token allowlist:

```solidity
mapping(bytes32 => bool) public isApprovedMarket;   // set in constructor
...
bytes32 marketId = keccak256(abi.encode(params));
if (!isApprovedMarket[marketId]) revert MarketNotApproved(marketId);
```

## LOW / INFO

### L-1 — Replay protection silently degrades on log corruption
`src/orders.py:151-155` — `_load_seen_nonces` swallows every exception per line (`except: continue`).
A truncated or corrupted line means its nonce is not registered as seen, silently reopening a
replay window for exactly that order. Prefer counting parse failures and surfacing them, or
failing closed when the corrupt-line count is non-zero.

### L-2 — Replay protection is off by default
`verify_signed_order(seen_nonces=None)` disables nonce checking. This is documented at
`orders.py:240-245`, but the safe default should be on, with opt-out for single-artifact inspection.

### L-3 — Rust dependencies unaudited; ZK soundness rests on a 0.1.x crate
`cargo-audit` is not installed, so `zk-mldsa` was not scanned. Note that `ml-dsa = "0.1.1"` is a
pre-1.0, not-independently-audited implementation, and the correctness of the entire on-chain PQ
attestation depends on it. Install and run `cargo audit`, and state this dependency risk in
`SECURITY.md`.

### L-4 — `AuditAnchor.anchor(bytes32)` overload has no sequence check
`AuditAnchor.sol:77-86` — the convenience overload skips race protection. Already documented in
NatSpec; consider removing it from the mainnet surface so a production path cannot accidentally
select it.

## Positive Security Practices Confirmed

- **No secrets in version control.** `git grep` for credential patterns over all tracked files
  returns nothing. `keys/*.sec`, `.env`, and build artifacts are gitignored; `.env` is `0600` and
  `keys/*.sec` are `0600` on disk.
- **The tx builder never touches private keys.** `src/monad_tx.py` constructs *unsigned*
  transactions only — no `from_key`, no `sign_transaction`, no key material in the process. Signing
  is delegated to an external wallet. This is the right architecture and eliminates a whole class of
  key-leak findings.
- **Both value-moving contracts are non-custodial**: `recipient: msg.sender` and
  `onBehalf = msg.sender` mean funds never rest in the contracts, and a lingering ERC-20 approval
  to the adapter cannot be drained by a third party (`safeTransferFrom` always pulls from
  `msg.sender`).
- **Solid Solidity hygiene**: `ReentrancyGuard` on both entrypoints, `SafeERC20`/`forceApprove`
  with allowance reset to zero, immutable allowlists, custom errors, explicit `deadline`, and
  `amountOutMin` correctly passed through as a true floor (the prior audit's H-1 economic leak is
  genuinely fixed).
- **Canonical-encoding hardening is unusually careful**: NFC normalization, sorted keys, compact
  separators, `allow_nan=False`, and a `default=` that raises rather than stringifies
  (`pq_signing.py:93-154`). These close real signature-malleability holes.
- **Audit log durability**: `flock` around read-prev-hash + append, `fsync` before unlock, and a
  correct doubling-window reverse scan for the last line (`orders.py:293-391`).
- **Streamlit is bound to loopback** with XSRF protection enabled and telemetry off.
- **Test suite**: 45/45 Foundry tests pass, including real mainnet fork tests against the live
  WMON/USDC pool and Morpho Blue.

## Recommendations (priority order)

1. **Fix H-1 and H-2 and redeploy both contracts** — effort: S. Two-line change each plus a
   redeploy and a `SUBMISSION.md` address update. These are live and cheap to exploit; do this first.
2. **Fix H-3** — effort: M. Commit `pkHash` in the guest, pin it in `MLDSAAttestation`, rebuild the
   guest, regenerate the Groth16 fixture, redeploy. Until it ships, correct the claim wording.
3. **Fix M-1** (pin trusted keys in the Python verifier) — effort: S. Also correct the
   "must break all three" claims in `pq_signing.py` and `orders.py` docstrings.
4. **Fix M-4** (market allowlist) and **M-3** (dependency upgrades) — effort: S each.
5. **Soften M-2 wording** in contract NatSpec and `SUBMISSION.md`, or implement a real gate — effort: S.
6. **Install and run `cargo audit`** (L-3); address L-1, L-2, L-4 as cleanup — effort: S.

Items 1–3 are the ones that matter for a Santander technical reviewer: two are live griefing
vectors on mainnet, and one is a gap between what the ZK circuit proves and what the writeup says
it proves.
